# 公開前提の防御を段階的に整える計画

## 目的と進め方

A②の優先度は5です。防御の方式、ソース、通信仕様、構築手順を公開し、利用者が公開物から検証できる構成を目指します。実運用の秘密鍵、席の認証情報、他人の手札といった権限に結びつく秘密は、その権限を持つ側で管理します。

光表現とPV制作の優先度10を維持し、カードの契約試験と配布の信頼境界を独立に整えます。各段階は、前段の成果を確認してから実装範囲を広げます。公開先への反映とCIは親の作業ブランチで扱います。

追加する検証は、所有するローカル試験環境で入力・状態・出力の契約を確認するものに絞ります。新たな脆弱性再現手順、任意プロセスへの操作、攻撃用クライアントは、この計画の追加成果に含めません。既存の試験とコードから保証したい性質を抽出し、通常のモジュール境界とテスト用データで確認します。

## 現在の基準

既存の実行記録は [公開前提のカード防御試験](OPEN_SECURITY_VALIDATION.md) にあります。同文書では、標準Windows Actionsの公開チェックアウト a7108089 でRust単体試験6本と実サーバー向け追加試験3本の成功を記録しています。本計画の作成時に、そのCIを再実行していません。

| 対象 | 読み取りで確認した実装 | 次段に必要な補足 |
| --- | --- | --- |
| カードの正本と操作 | Game::commandで操作番号、状態の版、手番、添字を検査。正しく採番された拒否操作も番号を消費する。操作と返信作成をMutex内で処理する | 拒否後に保持する状態と、仕様上変化する状態を契約表にする。同じ版を読んだ複数の正常操作の逐次化を確認する |
| 手札の配信 | Game::snapshotは0初期化した64バイトへ公開項目と本人の札だけを格納。既存単体試験は他席の札だけを変えて返信が一致することを確認する | 各席、初回待機、対局、切断待機、決着、再戦の各状態で同じ性質を確認する |
| 接続とTLS | 席のトークンで接続を固定し、TLSにライブラリを利用。期限と接続数・要求回数の上限がある | C++側の証明書照合・有効期間・資格情報送信順を含む既存TLS試験を、現行コミットのCIへ接続する |
| 起動時の配布整合性 | DistributionIntegrityがSHA-256とECDSA P-256、一覧・パス・上限・読み取りロックを検査する | 最初に信頼する公開鍵の配布と更新・失効・旧版の扱いを正式配布仕様にする |
| 夕景デモの署名 | CMakeのsunset_walkはengineへリンク。現行のdistribution_verifierとVERIFY_DISTRIBUTION定義はgameターゲット側に設定されている | 夕景デモを署名付き配布として出す場合、起動前検証と梱包入口の接続が必要。既存gameの署名設定を夕景デモへ一般化しない |
| 監査 | audit.rsは席別の返信をファイルに書き込んでflushする記録器 | ハッシュチェーンと署名チェックポイントは後続の設計対象。現在の記録器は対局の秘密を含むため公開しない |
| ローカル整合性 | WatchdogはCRC不一致を記録し、重複警告を抑えるため期待値を更新。深度検査・タグマスク・シャッフルも各経路へ接続済み | 公開環境の保証は、検知、拒否、秘匿を別々に定義する。Watchdogで自動復元やサーバー認証まで成立したという扱いを避ける |
| CIの実行範囲 | sunset-open-security.ymlは標準Windows上で夕景ビルド・WARPキャプチャ、Rust試験、追加3試験を実行する | 同CIはC++側のTLS試験とtest_distribution.pyを呼んでいない。GPU実機・別PC・実配布の検証も別途記録する |

根拠は [カードの正本](../../server_rs/src/lib.rs)、[接続と認証](../../server_rs/src/main.rs)、[TLS](../../server_rs/src/tls.rs)、[配布検証](../../engine/security/DistributionIntegrity.cpp)、[CMakeターゲット](../../CMakeLists.txt)、[監査記録](../../server_rs/src/audit.rs)、[現在のCI](../../.github/workflows/sunset-open-security.yml) です。

## 第1段階　公開する保証と信頼境界を定義する

設計レビューでは、利用者の端末を変更できる参加者、信頼する対局サーバー、公式配布を署名する管理者、公開コードを試験するCIを分けて図示します。

| 保証する性質 | 判断の基準 |
| --- | --- |
| 他席の秘密の非配信 | 公開項目と本人の手札が同じなら、他席の秘密だけを入れ替えても本人向け返信の全バイトが同じ |
| 公式対局の状態の正しさ | サーバーが検証し受理した操作だけが札、手番、結果を更新する |
| 操作の一度だけの適用 | 番号と版の条件に従い、既に確定した操作が二重に適用されない |
| 配布元の確認 | 信頼できる公開鍵から署名を確認し、一覧と全ファイルの内容が一致した場合に検証成功とする |
| 検証の再現性 | 公開コミット、固定した依存、条件、試験結果から同じ手順を実行できる |

完了条件は、正常操作と拒否操作の期待値、秘密の保管者、公開できる記録、想定する障害を1枚の契約表へ整理することです。端末内の描画だけの変更、既に見えた札の記憶、参加者の共謀、信頼するサーバーの管理者権限などは、後続の脅威モデルとして明記します。

## 第2段階　既存の防御をレビューし、契約試験を拡充する

Game::command、Game::snapshot、接続中の席、再接続の状態、C++の返信デコードを読む順番にします。追加試験では、公開の型とテスト用状態から性質を確認します。

| 契約試験 | 入力と観測 | 完了条件 |
| --- | --- | --- |
| 各席の返信の独立性 | サーバー内のテスト用状態で本人の札と公開枚数を固定し、他席の札の値を変える | 全席と各対局段階で64バイトの返信が一致。本人の札だけを変えた対照ケースでは期待した箇所が変わる |
| 許可された状態遷移 | 通常のRequest型から手番と番号・版の組を作る | 受理時に指定した状態だけが変わる。拒否時の番号消費など既存仕様も照合 |
| 操作の競合 | 同じ版を見た二つの通常の操作を、サーバーの処理境界で順に評価する | 一つの確定操作に追従し、後続が既定の結果となる。札の重複・欠損と手番の不整合が起きない |
| 切断と再接続 | 正常接続の停止と再開を行う | 正しい席、手札、対局番号、次の操作番号へ戻り、正常操作を続けられる |
| 失敗時の状態 | テスト用乱数取得エラーなど、既存のエラー経路を注入する | 札・席の所有・対局の更新が契約どおり。次の正常処理が成立する |
| 返信の整合性 | C++の公開デコーダーへ契約に沿う固定の返信を渡す | 版、予約領域、席、枚数、札の整合性が期待値と一致し、既存クライアントの動作を維持する |

既存のRust試験と追加3試験の実績は残し、新規試験は対象の性質と対応付けます。試行数だけで安全性を判定せず、どの入力範囲を確かめたか記録します。

完了条件は、新しい公開チェックアウトを標準Actionsでビルドし、契約試験と既存試験を同じコミットで通すことです。ログにはシナリオ名、期待した状態、成否、回数、コミットと実行URLを残します。

2026年11月18日に、各席の返信の独立性を試験する `snapshots_preserve_the_recipient_boundary_through_a_match` を追加しました。空の状態、参加待ち、対局開始、途中切断、再接続、進行中の各手、決着、再戦を通して全席の返信を比較します。他席の札の値だけを変えると返信全体が一致し、本人の先頭の札も変える対照ではその1バイトだけが変わります。初稿では毎回先頭の札を選ぶと対局が循環したため、固定シードで合法な添字を選ぶよう試験を修正しました。コミット `04e3380` の標準Windows ActionsでRust試験7件と既存の実サーバー試験3件に成功しました。 [試験結果](https://github.com/Qutalize/Noctis---Secure_Game_Engine/actions/runs/44221674830)

## 第3段階　TLSと認証の契約をクライアントまで確認する

既存のtest_tls.pyとC++のcard_client_probeを使い、証明書照合・有効期間・TLS接続・席への接続固定が通常の利用経路で機能するかを確認します。既存試験の追加実行方法は担当のレビュー対象とし、新しい攻撃コードを作成しません。

- テスト用証明書と席トークンを毎回分離して生成し、C++クライアントが認証前に信頼する接続先を確認する順序をレビューします。
- 証明書の更新と期限前の再配布、トークンの再発行と無効化の運用を設計します。
- 再接続時の正常な状態復帰と、通信期限にかかった場合の利用者向けの表示を確認します。
- 現行の標準Windows CIへC++の試験ビルドを追加し、別PCは後で同じ試験票で追試します。

完了条件は、Rustだけの判定に加え、C++の接続と表示に渡る通常の状態が同一コミットで確認できることです。別PCやインターネット向けの負荷評価は測定条件を別に管理します。

## 第4段階　署名付き配布を夕景デモへ接続する

既存の署名器、CNG検証器、test_distribution.py、配布監査を再利用します。夕景デモの起動前検証と梱包入口を接続し、レンダラー初期化より前に署名付き一覧を確認します。

1. 公開するファイル名、サイズ、SHA-256、配布版の識別方法と、必要なDXILの一覧を決めます。
2. 実験用の鍵はCIのその実行だけで作り、配布先に秘密部分を残しません。既存の配布テストで正規の署名付き構成と検証の結果を照合します。
3. 一覧と署名の仕様、起動前に利用者が公開鍵を確認する経路を文書化します。実行ファイルに埋め込む鍵は、この最初の信頼を引き継ぎます。
4. 本番用の署名鍵は、公開PRのビルドから切り離して管理します。公開PRでは本番Secretsを使わず、検証済みコミットを正式配布工程で署名します。
5. 鍵の更新・失効、配布版の識別と旧版へ戻す条件を、署名形式と更新処理の契約として追加します。初回検証と更新検証の責任範囲も明記します。

完了条件は、署名付きの夕景デモがクリーンな配布先から起動し、歩行・キャプチャ・終了が成立することです。既存game向けの試験結果と夕景デモの結果は対象ごとに記録します。Windows発行元署名を導入する場合は、証明書費用を含む別判断として扱います。

## 第5段階　回帰試験と証拠を同じコミットへ結びつける

標準Actionsを基本とし、各PRでは変更に関連するカード・配布・描画なしの試験を実施します。正常な対局と既存クライアントの互換性、署名付き夕景デモの起動と終了を統合時に確認します。描画はWARPで確認できた範囲と、GPU実機で確認した範囲を区別します。

| 残す証拠 | 内容 |
| --- | --- |
| 設計判断 | 課題、守る性質、採用した変更、比較した案、未解決の点 |
| 実行条件 | コミット、依存版、OS、ランナー、実機ならGPUとドライバー |
| 結果 | 正常ケース、失敗ケース、試行数、期待値との一致、実行URL |
| 性能 | CPU更新、GPU処理、画面提示、通信の確定を分けた測定 |
| AIの関与 | 試験案やコード補助に用いた範囲、実測で確認したこと、担当者の設計判断 |

秘密鍵、トークン、全席の札を含む監査原本はCI成果物へ掲載しません。必要な集計と、対局情報を除いた条件を短期保存します。ビルド・Rust targetなどの大きな生成物はCI側へ置き、開発PCへの複製を抑えます。

完了条件は、公開のソースと条件から試験を追試でき、同じコミットの配布物と結果を識別できることです。

## 第6段階　後続の防御レイヤーを個別に実証する

前段でカードと配布の境界を確認した後、描画や監査の経路を追加します。

| 後続テーマ | 設計する契約 | 依存と完了条件 |
| --- | --- | --- |
| FPSの可視性と光表現 | 正規に見える情報を一定にした二つのシーンで、秘匿対象の状態だけが変わっても、許可していない経路へ差が出ない | 夕景の固定カメラとリプレイを活用。本画面、影、反射、通信を対象ごとに計測。鏡越しの発見を許す条件もゲームルールに含める |
| コピーと寿命 | 複製するデータ、所有者、使用期間、消去のタイミングを定義する | コピーを数え、GPU参照が終わった領域だけを再利用。対象経路ごとの処理時間と残留を測る |
| 監査の署名 | 受理した操作の順序を確定し、署名付きチェックポイントを独立した保管先へ渡す | 既存の生返信記録と新しい監査仕様を分ける。未確定の末尾、サーバー再起動、保存失敗時の扱いを決め、CPU・通信負荷も測る |
| Webクライアント | 同じサーバーのルールと権限を、ブラウザーから利用しても維持する | サーバーのAPI契約と接続方式が固まってから対応。WebGPUの画面QAと認証・非配信の結果を個別に記録 |
| 別PCと将来のクラウド | 認証情報を各利用者に分け、信頼するサーバーを物理的に分離する | 同一PCの既存結果を基準に、機材・回線・遅延条件を追加。クラウド費用は実装前に別途見積もる |

この文書は段階計画と読み取りレビューです。各追加段階の実装・試験結果は、実際のコミットとCI実行に基づいて追記します。
